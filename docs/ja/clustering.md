# クラスタ

NextMQTT のクラスタはコーディネータ不要のメッシュです。各ノードが自分のセッションを
所有し、一致する購読を広告したピアへ publish を転送します。

## 要件

- 16 文字以上の共有 HMAC シークレット。
- 各ノードで到達可能な `AdvertiseUrl`（ピアが HTTP または HTTPS で呼びます）。
- ノード間で TCP 8080 が開いていること。
- 時計が 5 分以内に同期していること（署名付きリクエストのタイムスタンプは 5 分の
  窓を持ちます）。
- 一意な `NodeId`。

## 設定

```json
{
  "Cluster": {
    "Enabled": true,
    "NodeId": "node-a",
    "AdvertiseUrl": "http://node-a:8080",
    "Seeds": ["http://node-b:8080", "http://node-c:8080"],
    "Secret": "shared-secret-at-least-16-chars",
    "HeartbeatSeconds": 5,
    "NodeTimeoutSeconds": 20,
    "RequestTimeoutSeconds": 5,
    "MaxFiltersPerHeartbeat": 10000
  }
}
```

環境変数形式：

```bash
NEXTMQTT_CLUSTER__ENABLED=true
NEXTMQTT_CLUSTER__NODEID=node-a
NEXTMQTT_CLUSTER__ADVERTISEURL=http://node-a:8080
NEXTMQTT_CLUSTER__SEEDS__0=http://node-b:8080
NEXTMQTT_CLUSTER__SEEDS__1=http://node-c:8080
NEXTMQTT_CLUSTER__SECRET=shared-secret-at-least-16-chars
```

到達可能な seed は 1 つで足ります。メンバーシップは gossip で伝播するため、新しい
ノードは自動的にメッシュ全体から見えるようになります。

## メンバーシップ

- 各ノードは起動直後から heartbeat ループを始めます。
- heartbeat にはノード ID、Advertise URL、通常購読フィルタが入ります。
- 受信側は送信者をメンバー表にマージし、自分のメンバー表を返します。
- 受け取ったメンバーもマージされ、メンバーシップがメッシュ全体へ伝播します。
- `NodeTimeoutSeconds` を超えたノードは `suspect`、次に `dead` になり、3 倍の
  タイムアウト後に削除されます。

ダッシュボードの **Cluster** ページと `GET /api/v1/cluster` で現在のビューを確認
できます。

## 自己修復

- **停止ノードは削除されます。** `NodeTimeoutSeconds` の間沈黙したピアは `suspect`、
  次に `dead` となり、3 回のタイムアウト後に表から外れます。広告していたフィルタへの
  転送も即座に止まるため、クラッシュしたノードがトラフィックを引き寄せ続けることは
  ありません。
- **制限は即座に再計算されます。** ノードの参加・離脱で、接続・publish・トピック
  クォータのノードごとの配分を次の巡回を待たずに再計算します。クラスタ全体の値は設定
  どおりに保たれます。
- **実行中の参加は通常です。** 再起動したノードや新しいノードは到達可能な seed を
  1 つだけ必要とします。最初の heartbeat 応答からメンバー表をマージし、他のノードも
  同じ方法でそれを知ります。
- **retained は追いつきます。** 初回参加時に署名付き内部 API で 1 つのピアから
  retained 集合を取得し、元のタイムスタンプを保つため last-write-wins が維持されます。
  オフラインだった間に公開されたメッセージも失われません。
- **セッションレプリカはクラッシュに耐えます。** `SessionReplicaSeconds` ごとに永続
  セッションのスナップショットをピアへ送ります。所有者が停止し、クライアントが別の
  ノードへ再接続した場合、新しいノードは到達可能なら所有者からセッションを引き継ぎ、
  そうでなければ最新レプリカへフォールバックします。レプリカは所有者が生存していない
  場合、引き継ぎ時に到達できない場合、または生存中の所有者が「保持していない」と答えた
  場合（自身のファイル消失など）
  だけ使います。したがって古いコピーが、どこかで動いているセッションを復活させることは
  ありません。

セッションはクライアントに追従します。`CleanStart=false` で別ノードへ再接続すると、
前の所有者からセッションを引き継ぎ、オフラインキューと購読がノード変更をまたいで残り
ます。`CleanStart=true` は従来どおり新規セッションです。

## 可用性モデル

前提は「同時に 1 クライアントは 1 ノードにのみ接続し、切断後はクライアント自身が
再接続する」ことです。この前提の下で：

| 障害 | 影響 | クラスタの動作 |
| --- | --- | --- |
| クライアントの TCP 切断 | セッションがオフラインになる | 有効期限までキューが受け付け続ける |
| ノード停止 | そのセッションに到達不能、転送も停止 | `NodeTimeoutSeconds` で dead。購読者向けのメッセージは、クライアントが再接続して別ノードで引き継ぐまで失われる |
| 別ノードへ再接続 | セッションは停止ノード上 | 新しいノードが引き継ぐ。所有者がいない、到達できない、または「無い」と答えた場合は最新レプリカを使用 |
| 所有者のディスク消失、再起動 | セッションストアが空 | ピアのレプリカ（設定次第でファイル保存）から復元。「無い」と答えたピアはフォールバックを妨げない |
| 全ノード再起動 | メモリが空 | 各ノードがセッションとレプリカのファイルを再読込し、`(lastSeen, nodeId)` で最新を選ぶ |
| ネットワーク分断 | メンバーシップが二分割 | 実接続を持つ側だけがサービス。記録された所有者がローカルビューで生存している間はレプリカを使わない |
| レプリカ送信の遅延 | レプリカは最大 1 バッチ分（`SessionReplicaSeconds`。セッション数が `SessionReplicaBatchSize` を超えるとより長い）古い | 復元したセッションは最近のキューを欠くことがある |

**RPO**：レプリカ側のセッションは通常、最大 `SessionReplicaSeconds`（既定 5 秒）古い。
1 ラウンドで `SessionReplicaBatchSize`（既定 200）セッションを送るため、永続セッションが
それを超えるノードでは 1 周に `ceil(セッション数 / バッチサイズ) × SessionReplicaSeconds`
かかり、最も古いレプリカはその分古くなり得ます。所有者自身のファイルは最大
`SessionSnapshotSeconds`（30 秒）古い。retained は書き込みごとに保存。配信済みで未確認
のメッセージはキューから再送され、重複し得ますが MQTT は QoS 1/2 で許容します。

**RTO**：再接続と内部往復 1 回。新しいノードが生存ピアに問い合わせ、次に自分の
レプリカファイルを読みます。運用者の操作は不要です。

**意図的な制限**：送信 `inflight` の確認状態は移行しません。メッセージはキューから
再送され、二重に届くことがあります（QoS 1/2 で許容）。PUBREL を待つ受信 QoS 2 の
公開はセッションと一緒に移行するため、クライアントはペイロードを再送せずにハンド
シェイクを完了できます。期限 0 のセッションは複製しません（定義上、接続より長生き
できないため）。ノード間の順序保証も exactly-once もありません。

**分断時の判断**：セッションの所有権は合意形成ではなく証拠で決めます。生存中の所有者が
常に優先され、所有者が「セッションを持たない」と答えた場合は最新レプリカを使います。
復元された 2 つのコピーの同点は `(lastSeen, nodeId)` で決めるため、各ノードは調整なしで
同じ結論に達します。トレードオフは、分断された所有者と復元コピーが短時間だけ同じ
クライアント ID を受け付け得る点です。クライアント自体は 1 か所にしかいないため、
MQTT の意味論では許容できます。

## ルーティング

1. publish はまずローカルで配信されます。
2. クラスタが有効なら、ルーターは生存ピアを選びます：
   - retained の publish は全生存ピアへ送られ、retained 状態が収束します；
   - それ以外の publish は一致フィルタを広告したピアにだけ送られます。
3. ピアは HMAC 署名を検証し、メッセージ ID で重複排除して、再転送せずにローカルの
   ルーティング経路を呼びます。

```text
publisher ──► node-a ──► ローカル購読者
                  │
                  ├── 署名付き POST /internal/cluster/publish ──► node-b
                  └── 署名付き POST /internal/cluster/publish ──► node-c
```

遅い、または到達不能なピアはローカル配信を止めません。各転送には独自のリクエスト
タイムアウトがあり、失敗はデバッグレベルでログに残ります。

## retained メッセージ

retained の publish は全生存ノードへ複製されます。どのノードの新しい購読者も、SUBACK
の後に retained 値を受け取ります。retained メッセージの削除（空ペイロード）も複製
されます。

## 配信セマンティクス

- **経路ごとに at-most-once。** クラスタ転送はベストエフォート HTTP です。ピアが
  停止していると、そこへ向かうメッセージは失われます。MQTT の QoS はノードをまたぎ
  ません。
- **重複排除。** 有界の既視メッセージキャッシュが、同じクラスタメッセージの再配信を
  拒否します。
- **セッション親和性と引き継ぎ。** セッションは通常、接続を受け付けたノードにあります。
  クライアントが `CleanStart=false` で別ノードへ再接続すると、そのノードが前の所有者
  からセッションを引き継ぎ、購読とオフラインキューを復元して
  `session present = 1` を返します。旧接続は 0x8E で閉じられ、遺言は発行されません。
  PUBREL を待つ受信 QoS 2 はセッションと一緒に移動するため、クライアントは新しい
  ノードで PUBREL を送り、そこでメッセージがルーティングされます。
- **共有購読はクラスタ全体に広がります。** ノードは heartbeat で `$share` グループを
  広告し、各メッセージはグループをホストするちょうど 1 ノードに割り当てられます。
  選択はメッセージ ID とグループ名のハッシュで行うため、別ノードのグループメンバーが
  重複コピーを受け取ることはありません。
- **フィルタ伝播は結果整合です。** 新しいフィルタは次の heartbeat で広告されます。
  購読直後の publish は、次の heartbeat（既定 5 秒）までリモート購読者に届かない
  ことがあります。

## セキュリティ

内部 API は `timestamp.body` に対する HMAC-SHA256 を使い、5 分の時計ずれを許容します。
タイムスタンプと署名は `X-NextMQTT-Timestamp` と `X-NextMQTT-Signature` で送られます。

- シークレットは決してネットワーク上に送られません。
- ノード間トラフィックが信頼できないネットワークを越える場合は `AdvertiseUrl` に
  HTTPS を使ってください。
- ingress か NetworkPolicy で `/internal/cluster/*` を制限してください。
- シークレットの交換は新しい値でノードを再起動します。単一シークレットのため、
  ローリング交換はまだできません。

ダッシュボードのサインインはクラスタシークレットとは別です。各ノードは
`NEXTMQTT_ADMIN_TOKEN_SECRET` が設定されていなければ独自の鍵で Bearer トークンに
署名するため、あるノードが発行したトークンは別のノードで拒否されます。運用者が一度
サインインして任意のノードのダッシュボードや API を使う場合は、全ノードに同じ値を
設定してください。

## Kubernetes 固有の設定

StatefulSet は headless サービスと Pod DNS を使います：

```text
NEXTMQTT_CLUSTER__NODEID=$(POD_NAME)
NEXTMQTT_CLUSTER__ADVERTISEURL=http://$(POD_NAME).nextmqtt-headless.nextmqtt.svc.cluster.local:8080
```

seed は最初の 3 つの Pod 名を参照します。初期レプリカ数を超えてスケールしても、新しい
Pod が seed に接続し、gossip で発見されます。

## クラスタの検証

```bash
# メンバーシップ
curl -s http://localhost:8080/api/v1/cluster -H "Authorization: Bearer $TOKEN" | jq '.nodes'

# ノード間配信
dotnet run --project src/NextMqtt.Cli -- sub --port 1884 --topic cluster/# --count 1 &
dotnet run --project src/NextMqtt.Cli -- pub --port 1883 --topic cluster/test --message hello --qos 1
```

購読後、publish する前に少なくとも 1 heartbeat 待ってください。

## トラブルシューティング

| 症状 | 確認 |
| --- | --- |
| 一覧に 1 ノードしか出ない | ピアから `AdvertiseUrl` に到達できるか、seed の誤記、8080 のファイアウォール |
| ピアのログに `401` | シークレットの不一致、または 5 分を超える時計ずれ |
| ノードが alive/dead を繰り返す | heartbeat 間隔とタイムアウト、CPU  starvation |
| ピアで retained が欠ける | 同期導入前に参加したピア。再起動するか再公開 |
| リモート購読者がメッセージを逃す | フィルタ未伝播。1 heartbeat 待つ |
| リモート配信が重複する | メッセージ ID キャッシュの早期削除。ノードの時計と負荷を確認 |
| 再起動後に制限が低く見える | 停止ピアを 3 倍の `NodeTimeoutSeconds` まで数えている |
| 制限が低すぎる | `RateLimits` はクラスタ全体の値。ノード数で割られる |

## 制限

- セッション引き継ぎは購読、オフラインキュー、PUBREL 待ちの受信 QoS 2 を含みます。
  送信 `inflight` の確認状態は移行せず、キューから再送されるためクライアントは重複を
  見ることがあります。
- レプリカは通常、最大 `SessionReplicaSeconds` 古い。セッション数が
  `SessionReplicaBatchSize` を超えると最も古いレプリカは 1 周分古くなります。
  ファイルストアがない場合はメモリのみなので、全ノード再起動でレプリカが失われます。
  `Storage:Replicas:Mode` を `File` にすると再起動をまたいで保持できます。
- 引き継ぎと複製以外のノード間セッション永続化はありません。所有者と全レプリカ保持者、
  およびそのディスクが同時に失われるとセッションは失われます。
- フィルタ広告は全量スナップショットで、既定では heartbeat あたり 10,000 フィルタが
  上限です。
- クラスタルーティングはリンクごとに at-least-once で重複排除キャッシュを使います。
  トランザクション保証ではありません。
- retained 同期は参加時の 1 回だけです。メッシュから分断されたノードは、再接続するまで
  自分の古い retained 値を配信し続けます。
