# アーキテクチャ

NextMQTT はモジュラーモノリスです。1 つのプロセス、少数の明確なコンポーネント、
データプレーンとコントロールプレーンの明示的な境界で構成されます。このページでは
設計、データ構造、配信経路、トレードオフを説明します。

## 設計原則

1. **データプレーンの分離**：MQTT 接続、セッション、ルーティングは HTTP API や
   ダッシュボードから独立して動作します。遅い管理リクエストが publish を止めることは
   ありません。
2. **すべてを有界に**：セッションごとの inflight ウィンドウ、オフラインキュー、
   パケットサイズ上限、接続ごとの有界送信チャネル。バックプレッシャーはメモリの
   静かな増加ではなく、破棄メトリクスとして見えます。
3. **セッションの所有者は 1 つ**：クライアント ID は同時に 1 ノードだけが所有します。
   セッション乗っ取りは明示的で、ノード内では競合しません。
4. **制御系は交換可能**：REST API とダッシュボードはプロトコルエンジンと同じ Broker
   ファサードを使います。裏口はありません。
5. **クリーンルームの独立性**：挙動は OASIS MQTT 仕様に従い、他の MQTT 製品の
   内部実装には依存しません。

## コンポーネント構成

```text
                         ┌─────────────────────────────────────────────┐
   MQTT/TCP, MQTT/TLS    │                 NextMqtt.Server             │
   ────────────────────► │  Kestrel (API, ダッシュボード, WS /mqtt)      │
                         │  TCP/TLS リスナー (BackgroundService)        │
                         └──────────────────────┬──────────────────────┘
                                                │ ソケットごとに 1 つの ClientConnection
                         ┌──────────────────────▼──────────────────────┐
                         │                 NextMqtt.Broker             │
                         │                                             │
                         │  ClientConnection ──► BrokerSession         │
                         │        │                    │               │
                         │        ▼                    ▼               │
                         │  MqttBroker.RouteAsync ──► SubscriptionIndex│
                         │        │                    │               │
                         │        ├──► RetainedMessageStore            │
                         │        └──► ClusterRouter ──► ピア          │
                         │                                             │
                         │  ClientAuthenticator / TopicAuthorizer      │
                         │  BrokerMetrics / RateTracker                │
                         └──────────────────────┬──────────────────────┘
                                                │
                         ┌──────────────────────▼──────────────────────┐
                         │                  NextMqtt.Core              │
                         │  MQTT コーデック、トピックフィルタ、Trie    │
                         └─────────────────────────────────────────────┘
```

### `NextMqtt.Core`

- MQTT 3.1.1/5.0 のパケットモデル、デコーダー、エンコーダー、`PipeReader` フレーム
  リーダー。
- 厳密な UTF-8 とプロパティの検証。
- トピックフィルタの解析・一致と、購読・retained の両索引が使う汎用トピック Trie。
- ネットワークもログもサードパーティ依存もありません。

### `NextMqtt.Broker`

- `ClientConnection`：ソケット 1 つ、プロトコル状態機械、keep-alive、トピック
  エイリアス、送信チャネル、正常終了。
- `BrokerSession`：永続セッション状態、inflight ウィンドウ、オフラインキュー、
  受信 QoS 2 の重複排除。
- `MqttBroker`：認証、セッションの接続/乗っ取り、ルーティング、retained、
  管理、保守。
- `SubscriptionIndex`、`RetainedMessageStore`、`TopicAuthorizer`、
  `ClientAuthenticator`、`ClusterRouter`、メトリクス。

### `NextMqtt.Server`

- REST、ダッシュボードの静的ファイル、MQTT over WebSocket のために Kestrel を
  ホストします。
- 生の TCP と TLS のリスナーを動かします。
- 署名付きの内部クラスタ API をマップします。
- 管理者資格情報を初期化し、Vue バンドルを配信します。

### `NextMqtt.Cli`

- 共有コーデックを使う `pub`、`sub`、`bench`、`hash-password`。
- スモークテスト、クラスタ確認、負荷実験に便利です。

## 接続のライフサイクル

1. リスナーがソケットを受け取り、`ClientConnection` を作ります。
2. 最初のパケットは `Broker:ConnectTimeout` 以内の CONNECT でなければなりません。
3. クライアント ID を検証するか生成します。許可されていれば 0 長 ID にブローカーが
   割り当てます。
4. `ClientAuthenticator` はパスワード認証、パスワードフィールドの JWT、有効なら
   匿名アクセスの順に試します。
5. `MqttBroker.AttachSessionAsync` がノード内のセッション接続を直列化します：
   - clean start またはプロトコル変更なら古いセッションを破棄；
   - それ以外は既存セッションを再開（`session present = 1`）；
   - セッションが別ノードにある場合は、そのノードから引き継ぐか、所有者が停止して
     いる・保持していない場合に最新レプリカへフォールバック；
   - 生存中の前の接続は DISCONNECT `0x8E` を受け取ります（セッション乗っ取り）。
6. CONNACK を直接書き、送信ライターを開始して inflight とオフラインキューを
   フラッシュします。
7. 読み取りループは DISCONNECT、keep-alive タイムアウト、プロトコルエラー、
   ソケット障害までパケットを処理します。
8. クリーンアップで接続を切り離し、遺言を予約し、セッションを期限切れまたは保持し、
   セッション終了時に購読を解放します。

## データ構造

### トピック Trie

`TopicTrie<TValue>` はトピックレベルをキーとするプレフィックスツリーです。

- 購読の一致はトピックを辿り、完全一致ノード、`+` の子、`#` の子の値を集めます。
- retained の検索はフィルタを辿ります。`#` は部分木、`+` は子の反復、リテラルは
  下降です。
- `$` トピックの規則はルートで適用され、ワイルドカードが先頭の `$SYS` 風レベルに
  一致することはありません。
- 削除は空の枝を刈り、ノードのバケットは複数の値を持てます。

### 購読索引

- 通常の購読は実効フィルタをキーとする 1 つの Trie にあります。
- 共有購読は `(group, filter)` でまとめ、各グループはラウンドロビンのメンバー
  リストです。
- クライアント別の辞書が O(1) の参照と切断時の掃除を提供します。
- publish は `(subscription, sharedGroup)` の一致リストを生成し、ブローカーが
  クライアント単位で集約して重複配信を防ぎます。

### セッション

`BrokerSession` が所有するもの：

| フィールド | 用途 |
| --- | --- |
| `_inflight` | PUBACK/PUBREC/PUBCOMP を待つ送信 QoS 1/2 パケット |
| `_queue` | 永続セッションの有界オフラインキュー |
| `_inboundQos2` | PUBREL を待つパケット ID。重複配信を防ぐ |
| `_nextPacketId` | inflight の ID を避ける単調なパケット ID 割当 |
| `ExpiresAt` | 保守ループが評価する絶対的なセッション期限 |

セッションの変更はすべてセッションごとのロックを取ります。送信チャネルへの配信は
非ブロッキングで、満杯のチャネルはルーターを止めずに破棄として記録されます。

### retained ストア

retained メッセージは完全なトピックをキーにトピック Trie へ保存します。取得は購読と
同じワイルドカード意味論です。空ペイロードの retained publish はエントリを削除します。
メッセージ期限は絶対的な期限に変換され、読み取り時と保守時に適用されます。

## 公開経路

```text
PUBLISH ──► トピック/エイリアス検証 ──► ACL publish
        ──► retained 更新（retain 時）
        ──► 購読 Trie の一致
        ──► クライアント単位で集約（最大 QoS、RAP、購読 ID）
        ──► セッションのキュー/inflight ──► 接続の送信チャネル
        ──► クラスタ転送（通常購読 + retained レプリケーション）
```

配信時の QoS は `min(publish QoS, subscription QoS)` です。購読が
`retainAsPublished` を設定しない限り、ライブ転送では retain フラグを落とします。
SUBSCRIBE の購読識別子は MQTT 5 クライアントへの配信メッセージに付けられます。

## QoS 状態機械

**送信 QoS 1：** PUBLISH → PUBACK。確認されないパケットは
`Broker:RetransmitInterval` 後に DUP=1 で再送します。

**送信 QoS 2：** PUBLISH → PUBREC → PUBREL → PUBCOMP。PUBREL は PUBCOMP まで
再送します。

**受信 QoS 2：** PUBLISH をパケット ID で保存して PUBREC を送ります。メッセージは
PUBREL が届いてからルーティングし、その後 PUBCOMP を送ります。同じ ID の PUBLISH が
繰り返されても 2 回目の配信は作りません。

## クラスタ

ノードは署名付き HTTP のメッシュを作ります：

- 各ノードは heartbeat で**通常**購読フィルタを広告します。
- メンバーシップは gossip ベースで、応答に送信者のメンバー表が含まれるため、到達
  可能な seed は 1 つで足ります。
- publish は一致フィルタを広告した生存ノードにだけ転送します。retained の publish は
  全生存ノードへ複製し、retained 状態を収束させます。
- セッションスナップショットは `SessionReplicaSeconds` ごとにピアへ送られます。新ノード
  は所有者からセッションを引き継ぎ、所有者が生存していない、または保持していないと
  答えた場合だけ最新レプリカを使います。
- メッセージ ID が重複排除を提供し、リモートの publish は再転送しないためループを
  防ぎます。
- 共有購読はクラスタ全体で調整します。メッセージごとに共有グループ内の 1 ノードを
  選ぶので、ノードごとに 1 回配信されることはありません。
  [クラスタ](/ja/clustering)を参照してください。

内部 API はタイムスタンプと生の本文に対する HMAC-SHA256 で保護され、時計のずれは
5 分まで許容します。クラスタを有効にすると共有鍵が必須です。

## 並行性とバックプレッシャー

- 接続ごとに読み取りループ 1 つ、書き込みループ 1 つ。
- `System.IO.Pipelines` がフレーミング層でパケットごとの割当を避けてフレームを
  再構成します。
- 有界チャネル（1024 フレーム）がルーティングとソケット書き込みを分離します。
- セッションごとの inflight ウィンドウが未確認の QoS トラフィックを制限します。
- 保守ループが期限切れの retained とセッションを掃除し、再送を起動します。
- メトリクスが破棄と再送を公開するため、過負荷を観測できます。

## 耐久性と障害モデル

| イベント | 動作 |
| --- | --- |
| クライアント切断 | 期限が非ゼロ、または clean start でなければセッションを保持 |
| ブローカー再起動 | 有効なら retained と永続セッションをファイルから復元。無効なら失われる |
| クラスタ内のノード障害 | suspect → dead、3 倍のタイムアウトで削除。セッションは所有者のファイルか最新レプリカから復元 |
| クラスタ全体の再起動 | 各ノードがセッションとレプリカのファイルを再読込し、`(lastSeen, nodeId)` で最新を選ぶ |
| ネットワーク分断 | 各側でサービス継続。到達不能なピアへの転送は静かに失敗 |
| 遅い消費者 | 送信チャネルが満杯になり、メッセージを破棄して計数 |
| プロトコル違反 | 適切な MQTT 5 理由コードで接続を閉じる |

耐久性はデータ集合ごとにオプトインです：`Storage:Retained:Mode=File` は retained を
ジャーナルし、`Storage:Session:Mode=File` は永続セッションをスナップショットし、
`Storage:Replicas:Mode=File` はセッションレプリカを永続化します。送信 inflight の
確認状態は保存しませんが、メッセージ自体はスナップショット、レプリカ、引き継ぎでキューの形で再送されます
（重複し得ます）。PUBREL を待つ受信 QoS 2 の公開はスナップショットに含まれる
ため、ハンドシェイクを完了できます。retained は最後の値の保存であり、永続メッセージ
ログではありません。

## スケーリング

- 垂直スケールが最も簡単です。ホットパスは割当を意識し、ロック粒度はセッション単位と
  索引単位です。
- ノードはセッションを所有しますが、クライアントは任意のノードへ再接続できます。
  セッションは所有者から引き継ぐか、レプリカから復元します。
- クラスタルーティングのコストは広告フィルタ数とノード数に比例します。既定の上限は
  heartbeat あたり 10,000 フィルタです。
- 共有購読グループはノード間で調整されるため、メッセージはノードごとではなくグループ
  ごとに 1 回配信されます。

## NextMQTT が意図的に行わないこと

- 他社ブローカーのランタイム互換層や独自プラグイン API。
- 外部データベースの必須化。耐久性はノードごとのファイルベースです。
- 他社ブローカーとの互換性認証の主張。

これらの機能は将来、独立したモジュールとして追加される可能性があります。
[ロードマップ](/ja/roadmap)を参照してください。
